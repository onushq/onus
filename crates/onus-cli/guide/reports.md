# Reading a report

A report for the manifesto's example (1,408 changed lines in 23 files):

    ### Onus · 4 meaning-level changes · 1 needs attention · 1,408 lines in 23 files

    |   | Change                                                       | Kind                      | Why it matters |
    | ● | `notifications` now calls an external SMS provider (Acme SMS) | New external dependency   | Customer phone numbers leave the system via Acme SMS, a new vendor; needs a person |
    | ○ | `UserPreferences` gains an optional `phoneVerified` field     | Contract change, additive | Shared contract used in 4 files across 2 components; existing callers unaffected |
    | ○ | `notifications` subscribes to the `OrderShipped` event        | New event consumer        | Additive; `orders` is unchanged |
    | ○ | 1,402 lines of new code and tests inside `notifications`      | Internal                  | Stays inside `notifications`, which `billing` depends on; adds 69 test cases; ... |

    **Intent check:** not stated · **Boundary rules:** no new violations

## The headline

The number of meaning-level changes (rows), how many need a person, and the size of the text diff: lines added plus removed, and files changed. When nothing changed in meaning (only formatting, comments or moved files), the headline says "no changes in meaning".

## The rows

Each row is one change in meaning, computed from the code and described with a fixed template. Nothing in a row is generated by a language model.

- **● or ○**: ● means a person should look at this row. Onus marks a row this way when it is security-sensitive, breaking, a rules-of-the-game change (tests, CI, policies, onus.yaml, CODEOWNERS) or outside the stated intent.
- **Change**: what happened, in one line.
- **Kind**: the kind of change (`onus help changes` lists them all). "Outside stated intent · " is prepended when the row is an intent mismatch.
- **Why it matters**: the consequence, with the facts behind it: who depends on the thing that changed, which labels apply, what data leaves the system.

## Order

Rows are ranked so the one that deserves attention comes first. Changes outside the stated intent come first, then every row that needs a person (●), then the rest; within each of those, by kind:

1. changes outside the stated intent
2. security-sensitive changes
3. breaking changes (including boundary-rule violations)
4. new or changed dependencies
5. rules of the game (tests weakened, CI, policies, onus.yaml)
6. configuration
7. additive contract changes
8. new relationships (events, data, components)
9. tests
10. notable internal edits, then renames, then the internal rows

Within a group, rows Onus is unsure about come first (unknowns count as higher risk), then rows in components with sensitivity labels, then rows with a larger blast radius (more dependent files).

## Internal rows

Every row lists the lines it explains. The changed lines no row explains collapse into one internal row per component, such as "1,402 lines of new code and tests inside `notifications`". Its "why" says whether other components depend on that component, how many test cases were added, which new config keys are read, and whether some of the code could not be resolved.

## Intent check and boundary rules

- **Intent check**: "not stated" when no intent was given, "matches stated intent", or the number of changes outside it, followed by the reason for each. See `onus help intent`.
- **Boundary rules**: "none declared", "no new violations", or the number of new violations. Violations that already existed before the change are not reported.

## Evidence

The collapsed "Evidence per row" section lists, for each row, its kind and subkind, confidence, labels, blast radius, novelty and line counts, and every file and line behind it. Lines marked "(before the change)" are in the base tree, for example a deleted assertion.

## Structure only

Files that moved without changes, and files whose only changes are formatting, comments or updated import paths, are listed here instead of as rows.

## Map confidence notes

Code in the changed files that Onus could not resolve statically: dynamic imports, calls through computed members, event names computed at runtime, unresolved imports. Rows touching these files are marked low confidence. See `onus help troubleshooting`.

## The JSON report

`--format json` gives everything in the Markdown and more (schemas/semantic-report.schema.json):

- `summary`: counts of rows, rows needing attention, secrets, new rule violations and intent mismatches.
- `changes`: the ranked rows. Each has an `id`, `kind`, `subkind`, `level` (relationship, behavior or structure), `subject` (the map id it is about), `component`, `title`, `whyItMatters`, `hints` (labels, blastRadius, novelty, confidence, rulesOfTheGame, intentMismatch, needsPerson), `locations` (file, lines, side) and, for internal rows, `stats`.
- `intentCheck`, `ruleViolations`, `structure`, `textStats` and `mapDiagnostics`.

Output is deterministic: the same two trees always give byte-identical Markdown and JSON, with no timestamps or absolute paths.
